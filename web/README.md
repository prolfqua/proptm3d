# proptm3d browser app

This is the TypeScript frontend for an explicitly selected prepared output folder. Python `prepare` writes both the Parquet data and the static browser app; `serve` remains a separate static server. npm is needed only for browser development, not for normal analysis preparation or bundling.

```sh
npm ci
npm test
cd .. && make package-web   # copy the new build into the Python package
```

The checked-in `src/proptm3d/browser_static/` contains the production build shipped in the Python wheel. `make package-web` rebuilds and updates it; `make check` verifies it matches the TypeScript source. Python preparation installs those files and generates per-contrast static black-point backgrounds from Parquet. A portable ZIP can be produced with `proptm3d bundle DPA --in /path/to/viewer` immediately after preparation. The browser reads its protein catalog, sites, DEA results, sample abundances, protein features, structure-file metadata, and optional GSEA tables from Parquet; prepared method directories contain no CBOR files. `proteins.parquet` carries each protein's description from the source h5mu and precomputed UniProt and STRING links. Plot/detail contrast, GSEA method, running-curve sequence set and protein search stay above the collapsible filter. A limits the upper contrast choices; that contrast drives B's GSEA context and C's enabled Estimate operand, so switching it can change selected sites. The running-curve choice and protein search only navigate. The filter button/status below them turns red and names active branches. A compares significant-site sets across contrasts and restricts B's available GSEA contrast/result contexts by contrast name. B loads one compatible GSEA contrast at a time, comparing its FDR-eligible sequence_sets with optional leading-edge memberships. A, B and C support Off, All (union), whole-set and exact-intersection selection. Off disables only its branch. C combines their independently resolved site outputs with Estimate, Exposure and Region and defaults to **union**, not AND. Its All plot shows every observed exact combination, so its column counts partition the selected-site union. Disabled operands do not broaden that union. C contains its selection count and Off/All buttons. C Off preserves A/B filtering but ignores C's property operands. The global Filtering: On/Off switch beside Hide filters shows all measured sites without clearing A/B/C choices. Turning it Off collapses the filter panels; Inspect filters can reopen a would-be selection preview whose UpSet counts are not changed by the bypass. B selection narrows the GSEA sequence-set table and highlights its volcano points; the running curve inspects one set without adding another site filter. An active B locks the upper GSEA method, and B's selected sets plus the effective sites determine the upper running-curve choices.

All protein, detail, abundance, logo and plot-highlight views consume the model's effective deduplicated site identities, including measured sites with no estimate. Statistical plots preserve their background and distinguish selected significant/non-significant sites. GSEA's full curve is unchanged; selected hits are highlighted and its site table adds log2FC/site FDR. Search/paging affects display only. See [the browser guide](../docs/browser.md) for state transitions and examples.

The reusable, DOM-free site–set relation evaluator is in `src/membership.ts`; `src/upset-model.ts` holds display-only projections, and `src/upset.ts` builds the Plotly figure and interactive component. The component owns its Selected/All view state and top-left in-plot toggle. In every panel, its named-set Selected view puts the chosen set first and makes left bars count overlap within the matching intersections; View All restores global set sizes. This changes only the display, never exact memberships or site selection. `src/filtering.ts` owns the headless `FilterModel` that derives A/B/C membership relations and resolves C; `src/filter-panel.ts` renders that app-owned model and sends A/B/C selection commands. The GSEA controller supplies its payload and settings, not B's precomputed sets. Existing view controllers consume the model's effective sites rather than applying serial predicates. See the [filtering data model](../docs/filter-model.md) for its keys and boundaries. Original GSEA window ranks are joined by identity during preparation; re-run `prepare gsea` to correct already-prepared rank values.

`src/browser-profile.ts` defines the built-in profile contract and chooses Stats or GSEA from `run.json` capabilities. `src/stats-profile.ts` composes A+C and no enrichment controller; `src/gsea-profile.ts` adds B, GSEA navigation/Find content and a lazily created GSEA controller. `src/app-view.ts` and `src/filter-panel.ts` render only the profile's branches and controls while retaining one shared `FilterModel` and result workspaces. This is a code-level composition point, not a user-installable plugin loader.

The dependency path can be tested without mounting the browser: `src/filtering.ts` chooses A-permitted upper contrasts and resolves A/B/C memberships, `src/gsea.ts` resolves the compatible GSEA result and running-curve choices, and `src/filter-status.ts` formats the compact filter summary. The app and controllers call those same functions. Run `npx tsx --test tests/filter-dependencies.test.ts` for the synthetic Stats and GSEA contract checks.

Browser data, image, and model requests are restricted to the served origin; no automatic request goes to UniProt, STRING, AlphaFold, or a CDN. External protein links are opened only when clicked.

For development, run `proptm3d serve DPA /path/to/viewer` on port 8000, then `npm run dev` in this directory; Vite proxies the prepared data, structures, and PAE to that local server.
